# Architecture and data contract

Svelte renders engine data and collects scan/permission choices. A shared Svelte store owns application state and the bounded metrics buffer. Typed Tauri commands/channels handle IPC. Rust owns SQLite and all filesystem/diagnostic work. Tauri dialog APIs handle native folder selection. Narrow Rust commands handle Finder reveal and allowlisted System Settings destinations.

Rust modules: model (bridge-safe records), platform (allowlisted read-only macOS collectors), storage (metadata walker), database (migrations/queries), api (engine lifecycle and scan streams). Process execution uses fixed executable paths, argument arrays, bounded timeouts, and no shell interpolation. No privileges are requested by collectors.

Capabilities: supported, requiresPermission, manualOnly, unsupported, unknown, temporarilyUnavailable. Observations carry source/time/units/qualification. Scan states: running, complete, partial, cancelled, failed. Cancellation preserves partial results, and interrupted persisted runs are marked interrupted on startup. Missing collections do not erase successful collections.

Storage uses lstat, never follows symlinks, skips cloud placeholders and mount boundaries, deduplicates roots and hard links, and distinguishes logical/allocated bytes from filesystem capacity. The 0.8 whole-internal scope reviews all mounted internal volumes, using mounted filesystem identity alongside object identity and published APFS firmlink aliases. SQLite owns its frontier, deduplication and folder aggregation; see phases/whole-disk-cleanup.md. The metadata scanner performs no content reads, hashing or modification of inspected data. Separate explicitly requested Phase 2 content analysis is described below. Cache rules explain potential future cleanup; bytes are not promised recoverable.

SQLite is stored in ~/Library/Application Support/CoquiPCCleaner. Schema migrations run in transactions. Preferences, snapshots, evidence/findings and scan summaries persist locally; file inventory is replaced per successfully completed scope. Failed or cancelled scans remain inspectable without replacing a previous complete scope index. History defaults to 30 days. No raw file contents, serial numbers or command dumps in routine logging.

The Phase 1 scanner remains read-only. Phase 2.1 adds a separate `cleanup` module, typed review/approval/result models and Tauri commands. It never turns explanatory text into executable instructions. Native Foundation handles Trash; SQLite schema 2 persists review identities, approval, per-file intent and verification. See phases/phase-2-progress.md for eligibility, interruption/recovery rules and the pathname-race limitation. That legacy module exposes no permanent deletion, privileged helper or system-settings mutation API. The separately authorized 0.8 helper boundary is described below. Project-folder cleanup is a separate Phase 2.3 extension described below.

Version 0.2.1 classifies dedicated user caches separately from a standalone home package. Cleanup alone performs a bounded, no-follow read of home `package.json` to require a valid object without workspace configuration; raw contents are not retained and no scripts are executed. Repository/workspace markers and cache-local manifests remain exclusions. The scanner traversal remains metadata-only. The same checks run for candidates, preview and immediately before native Trash. The existing `CleanupFile.origin` carries review-time eligibility context, preserving SQLite schema 2 and old records.

Phase 2.2 adds `developer`, typed artifact/Git/worktree reports, guarded streamed Tauri commands and SQLite schema 3. Recognition uses the retained scan index; Git observations are refreshed on explicit recheck. Reports persist independently of transient UI state, become interrupted after app exit, and cascade with source-scan retention/purge. Developer analysis exposes no mutation operation. Its command environment, limits and eligibility distinctions are specified in phases/developer-artifacts.md.

Phase 2.3 adds `project_cleanup`, a separate preview command and paginated retained descendant inspection. It reuses the cleanup journal/approval/executor with a default-false project flag and private folder/manifest/Git seals. Whole supported directories use native Trash only after fresh checks and explicit regenerability acknowledgement; verification includes all descendant identities. Schema 3 remains compatible with old file records. Settings changes also share the operation guard so exclusions/retention cannot race active work. See phases/project-cleanup.md.


Phase 2.4 adds `duplicates`, `baseline`, `assistant`, `advice`, `resources`, `maintenance` and shared private `records` persistence helpers. Schema 4 retains typed diagnostic payloads and a separate opt-in schedule preference. Running payloads and index statuses recover as interrupted together. All diagnostic records share retention/purge; schedule/preferences survive diagnostic purge. Generated Tauri commands/channels expose bounded content jobs and baseline streams, cancellation, paginated history, local investigations, manual settings plans and assumption-based advice. New jobs reuse the Rust operation guard; the UI keeps cancellation visible across navigation. Duplicate approvals carry a default-false flag and private keeper/content seals; old cache/project records remain readable. No text response grants execution authority. See phases/phase-2-workflows.md for limits, manual capabilities, filesystem races and scheduler reservation/restart semantics.

Phase 3.1 adds `firmware` with fixed literal read-command variants, nonblocking bounded stdout/stderr, per-command timeout/cancellation and no shell, privilege prompt, download/install/reboot/security mutation flags. A dedicated request selects inventory/security/update checks per run; update-network acknowledgement is enforced by Rust. Tauri runs audits/outcome observations off the UI thread and streams actual stages and terminal reports. Firmware audits and manual Apple guidance plans use schema 4 typed records and existing retention/purge/interruption recovery. Guidance acknowledgement changes only its local journal state; a separate later read records observations with an explicitly unverified manual outcome. See phases/phase-3-implementation.md.

Phase 3.2 adds `firmware_review`, a pure retained-data module: no utility launcher, network client or OS notification API. Four typed IPC operations compare audits, read the notice center, save a reminder and dismiss a current notice. Comparison snapshots use `records` kind `firmwareComparison`; source readings retain their original timestamps/qualifications and are not unique-device attestation. SQLite schema 5 adds independent `firmware_preferences` for default-off reminder interval/next due and last dismissed source ID. Opening the app and the existing 30-second UI timer refresh local notices only. No OS background agent is installed. Dismissal coalesces missed reminders into one future interval; settings/prefs survive diagnostic purge, which removes comparisons/audits/notices and resets the evidence-dismissal pointer. Rust computes dates, validates chronological inputs and intervals, and serializes writes through the shared operation guard. See phases/phase-3-completion.md.

0.8 adds `volumes`, `applications`, `removal`, a narrow native Objective-C XPC/NSWorkspace adapter and schema 6. Whole-disk scope plans and categorized omissions persist with sessions. Inventory refresh is separate from indexed queries; removal/restore journals retain private identities and explicit action kinds without relaxing existing cleanup policies. The corrected health-only installation gate passed and was removed. Production `privileged`/`safe_fs` modules add strict typed XPC operations, a process-local native authorization session capped at 15 continuous minutes, explicit lock/off/app-exit behavior, independently verified native authorization on every request, one-use challenges, inert start reservations, process-bound progress/cancellation, independent descriptor-based removal validation and per-user root-only journals. Root-owned fixture/native lifecycle validation passed separately from package checks, including one interactive authorization request across the tested workflow; see phases/administrator-helper.md for scope and remaining limits. The fixed worker drops to the requesting user before native Trash resolution; root exclusive rename and separately approved restore never use root’s Trash or overwrite a destination. GUI public mirrors/imported metadata remain separate from private helper recovery records.
